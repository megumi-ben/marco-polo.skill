# 行程输出规范

写文件或接续旧行程时使用。本规范限定需要保存的内容，不要求用户填写结构化数据，也不要求一次生成全部文件。

## 文件职责

所有成果放在 `travel_plan/<城市-行程标识>/`；已有目录继续使用。

| 文件 | 何时生成、保存什么 |
|---|---|
| `行程数据.json` | ①开始维护：结构化需求、地点、选择、预约、日程、交通与来源 |
| `行程状态.md` | ①开始维护：已确认、当前假设、待决定、所处阶段和变更摘要 |
| `费用跟踪.csv` | ①开始维护：费用明细与人均总计，大交通跳过也要维护 |
| `大交通方案.md` | 仅需比较大交通时生成：候选、推荐、用户采用结果 |
| `住宿区域候选.md` | ②：区域比较与最终选择；已订酒店时简述既定住宿，不编候选 |
| `景点清单.md` | ③创建：候选及用户选择；④补齐入选详情，不另复制已选/详情清单 |
| `景点预约.md` | 入选后有预约或待核实预约事项时生成；全部已确认无需预约则不建空文件 |
| `每日行程.md` | ④路线分支：可执行日程及理由、交通、用餐时段/区域、预约摘要、预算、替代与检查 |
| `美食推荐.md` | ④美食分支：吃什么、去哪吃，按区域/类型组织，独立于每日路线 |
| `map.html` | ⑤：用户确认路线后制作，展示行程与地点；不自动加入推荐餐厅 |
| `food.html` | 美食资料就绪后制作：菜品、店家、实用信息与图片，无需等待路线确认 |
| `city-impression.html` | 城市和入选景点素材就绪后制作：城市特色、看点、游玩提示和图片，无需等待路线确认 |
| `index.html` | ⑤：导航骨架可提前搭建，子页分别验收后完成接入与整体验收，作为完整手册入口 |
| `config.local.js` | 地图需要时使用的本地配置，不把真实凭据写进说明、JSON或可分享模板 |

来源跟随事实保存，默认不另建来源汇总、城市介绍、坐标、图片或多份景点清单。复杂交通比较才按需增加专题文件；用户明确缩减交付范围时不创建未要求的页面。每阶段在对话中汇报结论和待决策项，不只输出路径。

## 共同约定

- JSON 保存事实与选择，预算明细以费用表为准；票价等原始报价可保存在对应资料中，但不重复入账。Markdown 和各页面展示同一份数据。用户修改可读文件后先吸收明确修改，冲突再澄清，不用旧数据覆盖用户修改。
- 地点、区域、预约、路段和费用使用稳定编号。景区与内部点可通过 `parent_id` 关联；酒店与街区不能因名称相近合并。一个预约或票种可关联多个地点，避免重复处理。
- 日期用完整年月日，时间注明目的地时区。未知值用 `null`，展示为“待核验”；已知免费才记 0。当前查询、估算、用户提供与官方核验的事实分别标明。
- 易变事实保留来源、查询日期、适用日期；核验状态落实到具体事实，不能用一个“已核验”覆盖整条景点。来源可以是有效链接或官方小程序/公众号的准确入口，不虚构 URL。
- 文档顶部标明行程、数据版本、更新时间及草案/待确认/已确认/需更新。确认的是用户选择与方案，不代表已订票；相关条件变化后标记受影响成果需更新。

## 行程数据.json

只保存结构化记录，不重复收录全部文档正文或抓取内容。约定以下模块，字段按实际需要展开，未知必需信息显式标记：

| 模块 | 必须承载的内容 |
|---|---|
| `meta` | 行程编号、城市、时区、版本、更新时间；城市名片需要时补简短城市介绍 |
| `requirements` | 日期/天数、实际到离边界、人数与限制、人均预算和包含范围、偏好强度、必去/避开、已知饮食限制/必吃与餐厅预约、已确认与假设 |
| `transport` | 已购/需规划/自理；候选及采用方案，到离站点时间，实际预订状态；金额引用费用编号 |
| `stay` | 区域候选、用户选择、区域参考点或真实酒店；酒店作为独立地点引用 |
| `places` | 编号、名称/别名、类型、片区、推荐理由/级别、用户选择、是否用户必去；位置、票务、开放、建议时段/时长、来源；城市名片复用的简介、看点、游玩提示与图片；具体餐厅记录类型、分店及地址，候选店家不等同于已选路线景点 |
| `food` | 研究时创建：菜品/小吃/饮品及推荐理由、口味限制；店家引用 `places` 编号，保存招牌、人均报价、排队/预约、替代选择及来源；不要求日期/路段关联，候选报价不自动计入预算 |
| `reservations` | 预约对象及关联地点、规则与入口、放票/操作时间、目标日期时段、实际结果、失败替代、来源 |
| `days` | 日期、起终点、按时间排列的活动、安排理由、备选和待落实条件；引用地点/预约/路段/费用编号 |
| `legs` | 起终点、方式、道路距离、预计时间、推荐理由、查询来源与日期、适用性/未核验说明；费用引用编号 |
| `sources` | 来源编号、链接或入口、支持的事实、查询及适用日期、官方/商业/经验等来源类型 |
| `decisions` | 用户确认的选择、相关版本、需保留的假设与重要变更；不逐条记录模型思考 |

地点的推荐级别使用 P0—P3；用户选择独立使用“待定/选中/备选/排除”，`must_visit` 单独表示用户必去。坐标至少有高德 POI ID（取得时）、地址、经度、纬度、坐标系、点位性质（入口/中心/住宿参考等）和匹配结果。

图片记录来源链接、图片链接、对应地点或菜品/门店及匹配级别，片区或门店环境图不标成具体景点/菜品实拍；缺图可空缺。菜品没有可靠位置时不造坐标。地图只采用行程中的点位，不能因餐厅存在于 `places` 就自动绘制。各分支在 `行程状态.md` 简记进度和未核验项，素材页已完成不代表路线已确认。

预约状态区分“待核验/无需预约/未放票/待预约/已预约/失败/已取消”。“已预约”须有用户明确告知或可靠结果，并记录实际日期时段；仅接受路线不能升级状态。

## 可读文档的固定内容

| 文档 | 内容与顺序 |
|---|---|
| `行程状态.md` | 需求与决定摘要 → 当前阶段 → 假设/待核验 → 待决定与下一步 → 重要变更，不复制全份日程 |
| `大交通方案.md` | 候选的日期、起终点、班次、时间、门到门耗时、价格依据、换乘和首尾日影响 → 推荐理由 → 采用结果 |
| `住宿区域候选.md` | 编号/名称/位置、评分依据、适合人群、交通可达性、价格倾向、优缺点、来源 → 用户选择 |
| `景点清单.md` | 顶部汇总用户选择，未选时明确待筛选；按类型或推荐级别展示可比较的候选、推荐理由、差异及基本时间/票务，突出优先推荐；入选项补简介、准确开放/入场/票务、建议时段/时长、地址/坐标/入口及核验来源，排除项不再做详细研究 |
| `每日行程.md` | 日期/住宿/强度/预算/关键前提 → 按天写主题和理由、起终点、活动时间、相邻交通、用餐时段/区域与休息、预约摘要、备选 → 费用与可行性检查 → 待决策项；普通餐厅不强制指定，已有固定餐饮需求保留 |
| `美食推荐.md` | 饮食需求与研究范围/来源缺口 → 吃什么（类型、特点、理由、忌口）→ 去哪吃（按区域/类型组织具体分店、招牌、地址、人均依据、营业、排队/预约、替代与来源）→ 待核验项；不按日期绑定，不把体验评价冒充核验事实 |

景点用简表加短说明；交通按天/路段说明方式、道路距离/耗时、费用依据和推荐理由，避免十几列宽表。地点的推荐与用户选择都要可见；入选项有安排或明确解释，排除项不得重新进入主线。

## 三个页面与统一入口

- `map.html`：只展示当前已确认日程中的地点、顺序与交通；普通用餐显示时间/区域，推荐餐厅不自动入图。用户选中的美食街/夜市照常展示，固定预约不遗漏。
- `food.html`：独立菜品与店家指南，按区域或类型浏览，展示来源和不确定项；不要求每日行程或地图密钥才能阅读。
- `city-impression.html`：城市简介与入选景点图文卡片，看点、游玩提示和图片来自既有资料，核心景点不能因缺图被省略；不依赖路线顺序或地图密钥。
- `index.html`：导航、切换、独立打开/返回与必要说明，复用子页，不保存另一套景点/日程事实。骨架可先建，子页验收后再完成整体交付；部分未完成时明示状态。

默认三页与入口一并交付；用户明确只要部分页面时遵从其范围。页面制作不重做研究或改变用户选择。更新公共事实时同步引用它的页面，单纯调整路线日期/顺序无需重写独立美食与城市名片。

## 景点预约.md

按接下来需要行动的时间排序，每项写：

- 预约编号、关联景点及实际预约对象，是否必须预约、票种/预约类别、官方入口。
- 提前几天/几点放票、规则适用范围、官方截止时间。没有截止时间就留空；“建议操作时间”另列。
- 拟游玩日期、目标及备选时段；未决定日期时保存规则和候选，不杜撰一个固定放票日。
- 当前状态、实际成功的日期/时段/人数、结果来源；未放票、未确认不能写已约。
- 失败时的替代及路线影响、核验来源与日期。

它是行程前的操作清单；每日行程只展示当天预约摘要，地图展示必要提示，均来自同一条预约记录。日期变化时重新计算相关操作时间并检查实际预订能否变更。不要在普通攻略里收集证件、订单凭据等无关个人信息。

## 费用跟踪.csv

用少量字段保存可追溯的金额，不另维护多份预算。固定表头：

```csv
记录类型,费用ID,类别,项目,费用口径,计费总额,分摊人数,人均金额,费用状态,来源,更新时间,备注
```

- `记录类型` 为“明细/汇总”；类别包含大交通、住宿、市内交通、门票、餐饮等。只将当前采用方案计入预算，候选报价留在比较材料中。
- `费用口径` 为“单人/共享”。单人机票、门票按一人份记录，分摊人数为 1；酒店/打车按本行实际总额和分摊人数记录。`人均金额 = 计费总额 ÷ 分摊人数`，备注说明覆盖几晚、几段或几张，不再重复乘数量。例如两人三晚房费合计 600 元，人均是 300 元。
- 美食候选的人均参考价留在推荐资料，不能将所有店铺叠加入账。日程可按实际采用的餐饮方案或用餐额度估算；选定具体餐厅后替换相关估算项，避免与原用餐预算重复计费。
- `费用状态` 为“已定/预估/待核验/已取消”。已定需用户明确已发生或已预订；采用推荐仍为预估。未知金额留空并单独列出，不能记 0。更正实际价格更新同一费用项，避免和估算重复计入。
- 不同成员票价或适用费用不同时，注明适用对象，分别展示各组人均；需要全团人均时按人数加权，不能直接相加各组均价。保留必要的已发生/不可退费用，取消方案不等于费用已退。
- 末尾保留三个汇总：已定人均总计、预估人均总计、全部人均总计；注明未知项，必要时在备注给全团总额。只累计有效明细，排除汇总行和已取消且无需承担的费用。

## 接续旧文件

旧行程已有 `行程需求.json`、候选/详情/坐标/图片 CSV、来源、美食或市内交通文件时，先读取并保留原文件，按本次工作所需吸收事实、来源和用户选择。先在状态中记清现行数据入口，后续以新数据生成相关视图；不为迁移重做全套查询，不擅自删除旧资料，不把旧确认变成待定。

已有多城市行程只更新本轮城市和相关到离边界，保留其他城市、全程预算及已定交通，不把单城市统计冒充全程总额。
